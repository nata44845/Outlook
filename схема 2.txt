ER‑диаграмма системы управления рисками по стадиям проекта: сущности и связи
Ключевая особенность модели: каждый риск привязан к конкретной стадии проекта (или нескольким стадиям), что позволяет анализировать уязвимости в динамике жизненного цикла.

Основные сущности
Проект

Атрибуты:

project_id (PK)

название

описание

дата_начала

дата_окончания

текущий_статус (например, «инициация», «планирование»)

общий_бюджет

Связь: один проект → много стадий, рисков, отчётов.

Стадия проекта

Атрибуты:

stage_id (PK)

project_id (FK)

название_стадии («инициация», «исполнение» и т. д.)

порядковый_номер

дата_начала_стадии

дата_окончания_стадии

статус_стадии

Связь: одна стадия → много рисков; одна стадия → много мероприятий.

Риск

Атрибуты:

risk_id (PK)

stage_id (FK)

название

описание

вероятность (1–5)

влияние (1–5)

уровень_риска (вероятность × влияние)

статус («идентифицирован», «в работе», «закрыт»)

дата_идентификации

Связь: один риск → одна стадия (или через ассоциативную таблицу — к нескольким стадиям); один риск → много событий и мер.

Категория риска

Атрибуты:

category_id (PK)

название («технические», «финансовые» и т. п.)

описание

Связь: одна категория → много рисков.

Мера управления (контрольное мероприятие)

Атрибуты:

measure_id (PK)

risk_id (FK)

stage_id (FK)

название

описание

стоимость

срок_реализации

ответственный_id (FK к Сотруднику)

статус («запланирована», «выполняется», «завершена»)

Связь: одна мера → один риск и одна стадия; один сотрудник → много мер.

Сотрудник

Атрибуты:

employee_id (PK)

ФИО

должность

email

отдел

Связь: один сотрудник → много мер управления.

Событие риска

Атрибуты:

event_id (PK)

risk_id (FK)

stage_id (FK)

дата_времени

описание

статус («произошло», «отклонено»)

Связь: одно событие → один риск и одна стадия.

Отчёт по рискам

Атрибуты:

report_id (PK)

project_id (FK)

stage_id (FK, опционально)

дата_создания

период_отчёта (дата_от, дата_до)

статус («черновик», «утверждён»)

содержание (текст/ссылка)

Связь: один отчёт → один проект и (опционально) одна стадия.

План реагирования

Атрибуты:

plan_id (PK)

risk_id (FK)

стратегия («избежание», «снижение», «передача», «принятие»)

список_мер (ссылки на measure_id)

сроки

ответственный_id (FK)

Связь: один план → один риск.

Мониторинг риска

Атрибуты:

monitoring_id (PK)

risk_id (FK)

stage_id (FK)

дата_проверки

текущая_вероятность

текущее_влияние

комментарий

Связь: один мониторинг → один риск и одна стадия.

Ключевые связи (с типами)
Сущность 1	Тип связи	Сущность 2	Пояснение
Проект	1 : N	Стадия проекта	Проект состоит из нескольких стадий.
Стадия проекта	1 : N	Риск	На каждой стадии выявляются свои риски.
Риск	1 : N	Событие риска	Один риск может реализоваться несколько раз на своей стадии.
Риск	1 : 1	План реагирования	Для каждого риска есть один план реагирования.
Риск	1 : N	Мера управления	Один риск может управляться несколькими мерами.
Мера управления	1 : 1	Стадия проекта	Мера реализуется на конкретной стадии.
Мера управления	1 : 1	Сотрудник	За каждой мерой закреплён ответственный.
Проект	1 : N	Отчёт по рискам	По проекту формируется несколько отчётов (в т. ч. по стадиям).
Стадия проекта	0 : N	Отчёт по рискам	Отчёт может быть привязан к стадии (не обязательно).
Риск	1 : N	Мониторинг риска	По риску ведётся мониторинг на каждой релевантной стадии.
Особые случаи
Риски, актуальные для нескольких стадий. Если риск пересекает границы стадий, вводят ассоциативную сущность Risk_Stage с полями:

risk_id (FK)

stage_id (FK)

актуальность_с (дата)

актуальность_до (дата).
Это позволяет явно указать, на каких стадиях риск значим.

Меры, действующие на нескольких стадиях. Аналогично: ассоциативная таблица Measure_Stage связывает меру с несколькими стадиями.

Примечания
Первичные ключи (PK) гарантируют уникальность записей.

Внешние ключи (FK) реализуют связи и обеспечивают целостность данных.

Кардинальность отражает бизнес‑логику: например, мера всегда привязана к одной стадии, а риск может быть связан с несколькими стадиями через ассоциативную таблицу.

Для визуализации используйте нотацию Crow’s Foot (прямоугольники для сущностей, линии с «вилками» для связей) или Chen (прямоугольники, овалы, ромбы).
